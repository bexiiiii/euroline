# Передача заказов в 1С — 27 октября 2026

Заказ сайта **U0HT3** (ID 4, 24 000 ₸) принят 1С. Документ **0000-000009**, GUID `5eb0606e-d171-11f1-8db8-ac1f6bdbe64e`, дата 27.10.2026. Проверено через OData: 6 × 4 000, итог 24 000, KZT. Документ непроведённый; статус оплаты на сайте не менялся.

## Причины

- `OrderService` сохранял событие в `order_outbox`, но Kafka-отправщик отключён. Отправщика для установленного `SI_RealtimeAPI` не было.
- Резервный CommerceML-экспорт обращался к S3 через `/storage`, который nginx удалял из подписанного пути. Хранилище возвращало `SignatureDoesNotMatch`.
- Установленный HTTP API 1С при повторе того же `commandId` фактически создавал новый документ. Проверка по одним только ключам из документации оказалась недостаточной.
- SiteIntegration v24.11 заполняет `Сумма` строки, но оставляет `СуммаСНДС`, итог документа и валюту пустыми.

## Исправление

- `modules/onecOrders` отправляет сохранённые события в HTTPS API 1С каждые 15 секунд. Сначала сохраняет неизменяемый JSON команды, затем отправляет. `commandId` равен UUID outbox; `siteOrderId` равен постоянному UUID заказа.
- Только явный `success=true`, `status=processed` и корректный GUID документа считаются подтверждением. `onec_ref_key` и `SENT` записываются после проверки документа.
- Перед первым созданием проверяются существующие документы по точному номеру сайта в первой строке комментария. При наличии `onec_ref_key` сразу проверяется этот документ. OData-фильтры этой публикации дают некорректный результат, поэтому проверка выполняется по постраничной проекции на стороне backend; предел 10 000 записей, при превышении — ручная проверка.
- Попытка фиксируется в БД **до** HTTP. После неопределённого результата POST или аварийного завершения выполняется только поиск/проверка документа, без повторного создания. Задержка увеличивается от 15 секунд; после 8 безрезультатных попыток восстановления — `FAILED` и ручная проверка. При этом заказ и JSON команды остаются в БД. Конкурирующие процессы используют `FOR UPDATE SKIP LOCKED`.
- Для v24.11 проверяются товарные строки через OData. У непроведённого документа заполняются только отсутствующие суммы и валюта. Изменённые товары, ненулевые конфликтующие суммы, налоговые или отменённые строки требуют ручной проверки.
- Когда прямой обмен включён, старые CommerceML-планировщик и обработчик экспорта отключены. Одновременное включение Kafka/старого push запрещено.
- Подписанные S3-запросы используют `S3_INTERNAL_ENDPOINT=http://rustfs:9000`. Публичные ссылки сохраняют прежний `S3_ENDPOINT`.
- TLS проверяется по предоставленному `astra_ca.crt`; проверка имени сервера включена. Учётные данные находятся только в серверном `.env`.
